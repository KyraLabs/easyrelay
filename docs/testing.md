# Testing

A relay is a protocol implementation exposed to untrusted input. The test strategy reflects
that: conformance and adversarial input carry more weight than unit coverage.

## Layers

### Unit tests

Colocated with the code in `test` blocks, run by `zig build test`. They cover pure logic:
filter matching, kind classification, tie-break resolution, varint encoding, token buckets.

Unit tests are not where correctness against the network is established. That is the next two
sections.

### Test vectors

`tests/vectors/` holds fixed inputs with known-correct outputs, taken from external sources
rather than generated by easyrelay:

- **BIP-340 Schnorr** — the official vector suite. Every case must pass, including the ones that
  must *fail* to verify.
- **Canonical serialization and event ids** — real events collected from the network, with
  their published ids. Coverage must include non-ASCII content, embedded newlines, tabs,
  quotes, backslashes, empty content, and empty tag arrays. These are the cases where a
  general-purpose JSON encoder diverges from NIP-01, and a wrong id makes the relay silently
  unusable.
- **NIP-44 and NIP-19** vectors where the dependency provides them, run as a regression check on
  the dependency itself.

Vectors run on every build. A dependency upgrade that breaks one is caught before it ships.

### Conformance tests

`tests/conformance/` implements [protocol.md](protocol.md) as executable checks, driven through
a real WebSocket connection to a relay instance with an in-memory store. One test per stated
rule, named after the rule.

Categories:

- Message framing and malformed input for each message type.
- Filter semantics: AND across fields, OR within fields, empty arrays, inclusive bounds,
  single-letter tag keys, non-hex values in hex-only fields, `limit` applying to stored events
  only.
- Ordering: newest-first, id ascending as tie-break, `EOSE` placement.
- Kind semantics: all four classes, both tie-break paths, the three equivalent empty-`d` forms,
  superseded events actually removed.
- Result prefixes: every prefix in [protocol.md](protocol.md#machine-readable-result-prefixes)
  reachable by a test that provokes it.
- Per-NIP suites written from the NIP text **before** the implementation, one directory per NIP.

A NIP's status in [nips.md](nips.md) flips to `supported` in the same commit that turns its
conformance suite green. That coupling is what keeps the NIP-11 document honest.

### Interoperability tests

Conformance tests check easyrelay against easyrelay's reading of the spec. Interop checks it
against what clients actually do.

- [`nak`](https://github.com/fiatjaf/nak) as the scripted CLI client, in CI.
- Manual smoke testing against at least two real clients per release.
- Phase 5 adds `strfry sync` as the NIP-77 reference peer, which is the only way to be confident
  in a reconciliation implementation.

### Fuzzing

Zig's built-in fuzzer, driven through the test runner with `zig build test --fuzz`, over every
parser that touches untrusted bytes:

- JSON message decoding.
- Event decoding and canonical re-serialization.
- Filter decoding.
- The NIP-77 frame decoder — the highest-risk target, because it decodes length fields from a
  peer and the reference implementation needs explicit overflow guards.

A fuzz target passes when a sustained run produces no crash, no hang, no leak, and no allocation
proportional to an attacker-supplied length field.

### Property tests

Randomised checks over invariants that examples cannot cover:

- Round-trip: an event serialized and reparsed yields the same id.
- Filter agreement: results from the LMDB store's index-driven planner equal the results from
  brute-force matching over the in-memory store, for randomised events and filters. This is the
  single highest-value test in the suite, because it validates the index design rather than the
  code that reads it.
- `COUNT` equals the length of the corresponding `REQ` result set.
- Replacement convergence: applying a set of replaceable events in any order yields the same
  survivor.

### Load and soak tests

Not run in CI; run before a release.

- Connection scale: hold the target connection count idle, measure memory per connection.
- Publish throughput: sustained accepted events per second at a fixed p99.
- Abuse: one flooding client alongside a well-behaved one; the well-behaved client must see no
  dropped events and no latency cliff. This is Phase 3's central exit criterion.
- Slow consumer: a subscriber that stops reading must be disconnected on its backpressure limit
  with relay memory flat.
- Soak: 24 hours of mixed traffic with no memory growth and no file-descriptor growth.

## Benchmarks

`bench/` holds the harness, in the repository, runnable by anyone.

Rules for published numbers, and they are not negotiable:

1. **Durable mode.** `storage.durable = true`. A number measured with durability disabled is
   labelled as such on every line it appears, or it is not published.
2. **Stated conditions.** Hardware, dataset size and shape, concurrency level, and easyrelay
   version accompany every figure.
3. **A named reference.** Comparisons run against a named implementation and version on the same
   hardware with the same dataset, in that implementation's default configuration.
4. **Reproducible.** The command that produced the number is in the repository.

These rules exist because the closest prior art in this space publishes self-reported figures
taken with durability disabled against competitors running durably. That comparison is not
meaningful, and repeating the mistake would make easyrelay's numbers worth nothing.

## Continuous integration

On every push and pull request:

1. `zig fmt --check`
2. `zig build test` on the pinned Zig version
3. Vector suite
4. Conformance suite
5. `nak` interop smoke test
6. Short fuzz run per target

Nightly: extended fuzzing and the soak test.

CI pins the exact Zig version from `.zigversion`. Zig is pre-1.0 and every release breaks
something; discovering that from a CI failure on an unrelated pull request is avoidable.
